# 발표 스크립트 초안 (5–7분)

## 1. 문제 제기 (30초)
"보안팀은 매일 수천 건의 방화벽/IDS 로그를 마주하지만, 그중 진짜 위협을 골라내고 대응하는 데는
시간이 걸립니다. 저희 팀 soara는 이 판단과 초기 대응을 AI Agent에게 맡기되, 실제로 차단하는
마지막 결정은 반드시 사람이 승인하도록 만든 자율 보안 대응 시스템을 만들었습니다."

## 2. 아키텍처 한눈에 보기 (1분)
- 로그 수집: Kinesis로 실시간 스트리밍 (파트A)
- 판단: Bedrock AgentCore 기반 단일 Agent가 Gateway를 통해 도구(checkIPReputation, blockIP)를
  스스로 호출 (파트B)
- 실행 통제: Step Functions가 위협도에 따라 분기하고, HIGH일 때만 사람 승인(SNS+SQS)을 거쳐
  차단 (파트C)
- "AI가 조사하고 판단하지만, 최종 차단 버튼은 사람이 누른다"는 점을 강조

## 3. 라이브 데모 (3분)
`demo_scenario.md` 순서대로 진행 (역할: A가 데이터/S3 화면, B가 Agent 호출, C가 Step
Functions/승인 화면 담당하면 자연스럽게 3인 릴레이 데모가 됨)

## 4. 설계 결정과 스코프 컷 (1분)
- "10시간이라는 제한 안에서 Multi-Agent 대신 단일 Agent + Tool Calling으로 스코프를 확정했고,
  3명이 A(데이터)/B(Agent)/C(오케스트레이션)로 나눠 앞 4~5시간을 거의 겹치지 않게 병렬로
  진행했습니다."
- 잘라낸 것: 실제 IP 평판 API 연동(자체 규칙으로 대체), Multi-Agent 분업, 실시간 웹
  대시보드(CLI로 대체)
- "실제 차단"이 아니라 DynamoDB 모의 기록으로 처리한 이유: 데모 환경에서 실제 인프라를 건드리지
  않기 위한 안전장치라는 점을 짧게 언급

## 5. 스트레치 목표 & 마무리 (30초)
- 시간이 남으면 시도한 것(또는 다음 단계로 제안하는 것): Multi-Agent 확장, 실제 IP 지역정보
  API, 웹 대시보드
- "이 구조는 Human-in-the-Loop 패턴이라 다른 보안 대응, 결제 승인, 인프라 변경 등 '자동화하되
  최종 결정은 사람이' 필요한 어떤 워크플로에도 그대로 재사용할 수 있습니다."로 마무리

## Q&A 대비 예상 질문
- "실제 운영에 쓰려면 무엇이 더 필요한가요?" → 실제 방화벽/보안그룹 API 연동, IP 평판 외부 API,
  오탐 방지를 위한 화이트리스트, 승인자 인증/권한 관리(현재는 CLI로 단순화)
- "왜 SQS를 SNS와 같이 썼나요?" → SNS는 사람에게 알리는 용도(이메일), SQS는 Step Functions가
  taskToken을 들고 대기하다가 승인 응답을 콜백받는 용도로 역할이 다릅니다.
- "3인 역할을 어떻게 나눴나요?" → A/B는 초반에 완전히 독립적으로 진행(B는 A의 데이터 없이도
  Cognito/Gateway 뼈대를 먼저 진행 가능), C는 아직 없는 Lambda를 임시 Pass 상태로 채워두고
  단계적으로 실제 로직으로 교체하는 방식을 써서 A/B가 끝나기 전에 먼저 시작했습니다.
