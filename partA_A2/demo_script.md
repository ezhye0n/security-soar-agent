# Security SOAR Agent — 슬라이드별 발표 대본 (7분 버전)

> 총 목표 시간: 약 7분(423초). 슬라이드 장수가 많아서 두 쌍(①데이터 선정+로그 스트리밍, ②Sliding Window 관련 2장)을 각각 한 호흡으로 묶어 진행하는 걸 추천합니다. 순서/생략은 자유롭게 바꾸셔도 되는 걸로 알고 있어서, 아래 흐름이 자연스럽다고 판단해 이 순서로 정리했습니다. 빈 슬라이드(구분용으로 보이는 것)는 건너뛰었습니다.

---

### 1. 프로젝트 소개 (10초)

"안녕하세요, 저희는 팀 soara입니다. 오늘 보여드릴 건 실시간 보안 위협 탐지부터 AI 분석, 사람의 승인, 자동 차단까지 이어지는 SOAR(Security Orchestration, Automation and Response) 파이프라인입니다."

### 2. 문제 정의 및 프로젝트 목표 (35초)

"보안 관제 담당자는 하루에도 수천, 수만 건의 네트워크 이벤트를 마주합니다. 여기엔 세 가지 근본적인 문제가 있습니다.

첫째, 사람이 실시간으로 모든 트래픽을 눈으로 확인하는 건 물리적으로 불가능합니다.
둘째, 자동으로 탐지는 하더라도 '왜 위험하다고 판단했는지' 근거 없이 점수만 던져주면, 담당자가 신뢰하고 실제 대응으로 옮기기 어렵습니다.
셋째, 탐지되자마자 AI가 곧바로 차단해버리면, 오탐(false positive) 한 번으로 정상 서비스가 멈추는 사고로 이어질 수 있습니다.

저희 목표는 이 세 가지 문제 — 확장성, 설명 가능성, 안전한 자동화 — 를 동시에 해결하는 파이프라인을 만드는 것이었습니다."

### 4. 전체 시스템 아키텍처 (40초)

[아키텍처 다이어그램]

"전체 흐름은 이렇습니다. 실시간 트래픽을 Kinesis로 스트리밍하고, Consumer Lambda가 슬라이딩 윈도우로 위협 점수를 계산해 DynamoDB와 S3에 기록합니다. HIGH로 판정된 IP는 자동으로 담당자에게 승인 요청이 가고, 담당자가 승인해야만 실제로 차단됩니다 — 탐지는 자동, 최종 결정은 사람이 하는 구조입니다. 여기에 Bedrock AgentCore 기반 AI 에이전트가 추가 판단 근거를 제공하고, 이 모든 과정은 실시간 대시보드에서 확인할 수 있습니다. Lambda, Kinesis, DynamoDB, S3, Step Functions, SNS, Bedrock AgentCore까지 전부 AWS 서버리스로 구성했습니다."

### 5. 데이터 선정 및 전처리 + 실시간 로그 스트리밍 구현 (25초)

[두 슬라이드를 한 호흡으로]

"데이터는 CTU-13이라는 보안 연구용 봇넷 트래픽 캡처 데이터셋을 사용했습니다. 실제 감염된 호스트의 트래픽이 라벨링되어 있어서 신뢰도 있는 검증이 가능하다는 점이 선정 이유입니다. 원본 바이너리 플로우 데이터를 파싱해서 ALLOW/BLOCK 라벨이 붙은 형태로 전처리했고, 이걸 Producer가 Kinesis로 실시간처럼 재생하도록 구현했습니다."

### 6. 왜 Sliding Window인가? + Sliding Window 기반 실시간 위협 탐지 (30초)

[두 슬라이드를 한 호흡으로]

"왜 단순 누적 카운트가 아니라 슬라이딩 윈도우를 썼는지 말씀드리면, 봇넷 공격은 짧은 시간에 몰아치는 버스트 패턴이 특징입니다. 하루 전체 누적으로 보면 이런 패턴이 희석돼서 놓치기 쉽고, 반대로 순간 스파이크만 보면 오탐이 늘어납니다. 그래서 저희는 최근 5분(300초) 구간만 보는 슬라이딩 윈도우 방식을 택했습니다. 이 윈도우 안에서 BLOCK 이벤트가 5회 이상이면 HIGH, 2회 이상이면 MEDIUM으로 실시간 판정합니다."

### 7. AI Agent 기반 자율 대응 (30초)

"규칙 기반 판정에 더해서, 저희는 Amazon Bedrock AgentCore 위에 Strands Agent 프레임워크로 AI 에이전트를 구현했습니다. 이 에이전트는 MCP 프로토콜로 연결된 위협 조회 도구를 직접 사용해서 IP를 조사하고, CTU-13 데이터셋 특성상 정상 트래픽이 98.5%나 되기 때문에 BLOCK 한두 건만으로는 섣불리 판단하지 않는다는 도메인 지식까지 반영해서 사람이 읽을 수 있는 자연어 설명을 제공합니다. 다만 이 에이전트는 판단과 설명까지만 하고, 절대 스스로 차단을 실행하지 않습니다."

### 10. medium 화면 설명 (15초)

"이 화면은 MEDIUM 단계입니다. 최근 5분 안에 BLOCK이 2~4회 발생한 상태로, 아직 확정적이진 않지만 주시가 필요한 수준이라는 뜻입니다."

### 11. high 화면 설명 (15초)

"BLOCK 이벤트가 계속 누적되면서 HIGH로 올라간 화면입니다. 위협 점수 100점, 판정 근거까지 자동으로 표시됩니다."

### 12. IP 차단 승인 요청 이메일 발송 화면 설명 (20초)

"HIGH로 판정되는 순간, 시스템이 자동으로 차단하지 않고 담당자에게 이렇게 승인 요청 이메일을 보냅니다. Step Functions가 담당자의 응답을 기다리는 대기 상태로 들어갑니다."

### 13. IP 차단 승인 및 실제 차단 — Step Function 그래프 전/후 (30초)

[전: 대기 중 그래프 → 후: 승인 완료 그래프]

"승인 전에는 이렇게 Notify 단계에서 대기 상태로 멈춰 있습니다. 담당자가 승인하면, Step Functions가 이어서 BlockIP 단계를 자동으로 실행하고, 그래프 전체가 성공으로 완료됩니다. 사람이 최종 결정을 내리는 순간이 명확하게 기록되는 구조입니다."

## 예상 Q&A 대비

- **Q: 왜 완전 자동 차단이 아니라 승인을 받나요?**
  A: 오탐(false positive)으로 정상 트래픽/서비스가 차단되는 사고를 막기 위함입니다. 탐지 속도는 그대로 유지하면서, 실제 액션(차단)에만 사람의 확인을 요구하는 구조입니다.

- **Q: 승인 안 하면 어떻게 되나요?**
  A: 1시간 동안 응답이 없으면 자동으로 타임아웃 처리되어 차단되지 않고 종료됩니다.

- **Q: 점수(score)는 어떻게 계산되나요?**
  A: 최근 5분(300초) 안에 그 IP가 몇 번 BLOCK됐는지를 HIGH 기준(5회)으로 나눠서 0~100으로 환산합니다. 기준을 넘으면 100으로 고정됩니다.

- **Q: AI 에이전트는 왜 자동 호출이 아니라 버튼 방식인가요?**
  A: 에이전트 호출 자체가 LLM 추론 + 외부 도구 조회가 들어가는 비용/시간이 드는 작업이라, 담당자가 실제로 필요할 때만 온디맨드로 호출하도록 설계했습니다.

- **Q: AI 에이전트가 틀리게 판단하면 어떻게 되나요?**
  A: 에이전트의 판단은 참고용 설명이고, 실제 차단 여부는 어디까지나 사람이 결정합니다. 에이전트는 설계상 blockIP를 절대 스스로 호출하지 않습니다.
